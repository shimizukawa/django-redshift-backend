Schema and migration compatibility
==================================

Upgrading django-redshift-backend does not create or apply a Django migration.
It also does not inspect, change, or repair existing Redshift tables. Review
the migration SQL generated by your application and decide explicitly whether
an existing database needs a user-owned repair migration.

DISTKEY migration compatibility
-------------------------------

Older releases serialized ``DistKey`` as ``AddIndex`` but silently ignored the
database operation. Newly applied migrations now emit ``ALTER DISTKEY``. This
is a correction for future migration application; it does not modify a table
whose historical migration has already been recorded as applied.

Inspect an existing table before deciding to repair it::

    SELECT "column", distkey
    FROM pg_table_def
    WHERE schemaname = 'your_schema' AND tablename = 'your_table'
    ORDER BY sortkey, "column";

If the application confirms the intended key, it can add its own migration::

    from django.db import migrations

    class Migration(migrations.Migration):
        dependencies = [("your_app", "previous_migration")]
        operations = [
            migrations.RunSQL(
                'ALTER TABLE "your_schema"."your_table" '
                'ALTER DISTKEY "customer_id"',
            ),
        ]

Replace every placeholder consistently with the inspected schema and table.
This manual repair is intentionally irreversible: Redshift can preserve a
large table's distribution key when changing it to automatic distribution.
Provide a ``reverse_sql`` only when the application has recorded and can
recreate the exact pre-repair distribution state. The backend never runs this
correction automatically. See the Amazon Redshift `ALTER TABLE documentation
<https://docs.aws.amazon.com/redshift/latest/dg/r_ALTER_TABLE.html>`_ for the
authoritative syntax and restrictions.

SORTKEY changes
---------------

``SortKey`` values in ``Meta.ordering`` affect table creation. Django does not
turn later ordering changes into schema operations, so changing the sort key of
an existing table needs an explicit application migration, such as ``RunSQL``.
Review the `CREATE TABLE documentation <https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_TABLE_NEW.html>`_
when choosing the new key.

Persistent defaults on non-null columns
---------------------------------------

Redshift can add a non-null column with a ``DEFAULT`` but does not document
``ALTER COLUMN DROP DEFAULT``. A literal Python default used while adding or
recreating a non-null column therefore remains a database ``DEFAULT`` for
compatibility with older backend releases. A literal ``db_default`` is handled
the same way. A non-null operation with no supported literal default is
rejected; the backend never invents a replacement value such as ``0``, an
empty string, or the current time.

Informational constraints
-------------------------

Redshift does not enforce ``PRIMARY KEY``, ``FOREIGN KEY``, or ``UNIQUE``
constraints, but its planner can use them. Data-loading processes must keep
every declared relationship true. Incorrect metadata can lead to incorrect
query plans or results. See Amazon Redshift's
`constraint guidance <https://docs.aws.amazon.com/redshift/latest/dg/t_Defining_constraints.html>`_
before declaring these constraints.

Supported boundaries
--------------------

Redshift does not support ordinary secondary indexes. Explicit ordinary index
operations fail rather than being silently ignored. Unsupported constraints
and table or field options likewise fail explicitly. Altering a field that is
a table key (a ``DISTKEY`` or ``SORTKEY`` field) through column recreation is
also rejected, because that operation needs an explicit, reviewed migration
plan.

Non-atomic recreation
---------------------

Most type reductions and nullability changes recreate a column with ``ADD``,
``UPDATE``, ``DROP``, and ``RENAME`` statements. The sequence is not atomic.
Review ``sqlmigrate`` output and take an appropriate backup before applying
it; this backend does not advertise transactional DDL rollback.

Live verification against Redshift remains deferred because this release has
no real cluster available. The AWS documentation is the authoritative contract
for the generated DDL in this release.
